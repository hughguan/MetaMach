# Agent Planner Design — LLM-Assisted Pipeline Generation

 > **状态：✅ ADR-022 已批准 (0.5.0).** 详见 `docs/ADR.md` ADR-022。
> 
> **Scope lock:** 0.5.0 — after the Pipeline DAG engine (0.5.0) ships. The Planner generates `pipelines/*.toml` files; without a DAG engine to execute them, the Planner has no runtime target.
>
> **Prerequisites:** Phase 0b (workflow engine, 0.4.0) → Pipeline DAG engine (0.5.0) → Agent Planner (0.5.0).

---

## 🪐 Concept

The Agent Planner replaces manual drag-and-drop Pipeline editing with **natural-language Pipeline generation via LLM**. The Factory Director describes the desired pipeline in plain language; the Planner selects reusable Workflows from the library, assembles them into a Pipeline DAG, and writes a validated `pipelines/<name>.toml` file — ready for immediate dispatch by the 0.5.0 DAG engine.

```
 💬 Director: "Build an M5Stack compile-and-flash pipeline, with human
              approval required before flashing to /dev/ttyUSB0"

        │
        ▼
 🤖 Agent Planner (LLM-backed, CLI-driven)
        │
        │  1. Searches the Workflow library (workflows/*.toml)
        │  2. Selects wf_cargo_build + wf_esptool_flash
        │  3. Generates a Pipeline DAG with HITL gate
        │  4. Validates via `janus pipeline validate`
        │  5. Writes pipelines/m5stack_release.toml
        │
        ▼
 ✅ Ready to dispatch: janus dispatch --pipeline m5stack_release
```

---

## 1. What the Planner Generates

The Planner produces **standard 0.5.0 Pipeline TOML** — no custom DSL, no YAML. The output is identical to hand-written pipeline files:

```toml
# pipelines/m5stack_release.toml（generated by Agent Planner）

[pipeline]
name = "m5stack_release"
description = "M5Stack firmware build + flash with HITL approval"

[[nodes]]
id = "build_firmware"
workflow = "wf_cargo_build"

[[nodes]]
id = "flash_hardware"
workflow = "wf_esptool_flash"
needs = ["build_firmware"]
hitl_gate = true
```

This is the exact same format the 0.5.0 Pipeline engine consumes — the Planner is a **generator**, not a new execution layer.

## 2. Three-Phase Interactive Workflow

### Phase 1: Draft Generation

```
Input:  Director's natural-language description
Action: LLM searches the Workflow library, selects candidate workflows,
        generates initial Pipeline TOML
Output: Draft TOML displayed to Director for review
```

The LLM uses the Workflow library (`workflows/*.toml`) as its tool catalog. Each workflow's `name` and `description` fields provide the LLM with enough context to select the right ones.

### Phase 2: Interactive Revision

```
Input:  Director's feedback ("add baud rate 115200", "retry compile twice")
Action: LLM revises the TOML — adds node parameters, adjusts DAG edges,
        inserts HITL gates
Output: Revised TOML with changes highlighted
```

The Planner shows the DAG topology as ASCII art so the Director can verify the structure before committing.

### Phase 3: Validation & Commit

```
Input:  Director approval ("y")
Action: `janus pipeline validate <path>` — checks TOML syntax, DAG acyclicity,
        Workflow references, and Absurd PG schema compatibility
Output: Pipeline written to pipelines/<name>.toml; daemon can dispatch immediately
```

## 3. Implementation Design

### 3.1 CLI Surface

```bash
# Start an interactive planning session
janus pipeline plan

# Plan against a specific blueprint context
janus pipeline plan --blueprint gatemetric

# Validate a generated pipeline without committing
janus pipeline validate pipelines/m5stack_release.toml
```

### 3.2 LLM Integration

The Planner is a **CLI tool** that calls an LLM API (the same Coding Plan provider already configured for Pi). It does not run inside `janus-daemon` — it's a client-side tool like `janus onboard`.

```
janus pipeline plan
  │
  ├─► Read workflows/*.toml (Workflow library)
  ├─► Send library catalog + user prompt → LLM API
  ├─► Receive generated TOML
  ├─► Display + interactive revision loop
  └─► Write pipelines/<name>.toml
```

**Key design decisions:**
- **Not in the daemon.** The Planner is a CLI client — it calls the LLM, generates TOML, and exits. No long-running LLM process inside MM-CORE.
- **Uses existing LLM provider.** The Coding Plan provider configured for Pi (`ZAI_CODING_CN_API_KEY`) can serve the Planner's LLM calls.
- **Deterministic validation gate.** The LLM is an assistant, not an authority. `janus pipeline validate` is the final gate — invalid TOML is rejected regardless of what the LLM generated.

### 3.3 Workflow Library Discovery

The Planner reads the Workflow library from `workflows/*.toml`:

```rust
// janus pipeline plan: discover available workflows
fn discover_workflows(repo_root: &Path) -> Vec<WorkflowSummary> {
    std::fs::read_dir(repo_root.join("workflows"))?
        .filter_map(|e| e.ok())
        .filter(|e| e.path().extension().map(|x| x == "toml").unwrap_or(false))
        .filter_map(|e| {
            let wf: Workflow = toml::from_str(&std::fs::read_to_string(e.path()).ok()?).ok()?;
            Some(WorkflowSummary {
                name: wf.workflow.name,
                description: wf.workflow.description.unwrap_or_default(),
                step_count: wf.steps.len(),
            })
        })
        .collect()
}
```

The catalog sent to the LLM is minimal — just name, description, and step count. The LLM doesn't need to see full step details to assemble a DAG.

## 4. Dependency Chain & Blockers

```
Phase 0b (0.4.0)  →  Pipeline DAG (0.5.0)  →  Agent Planner (0.5.0)
  workflow.rs          pipelines/*.toml          janus pipeline plan
```

| Prerequisite | Status | Why Blocking |
|---|---|---|
| Phase 0b (workflow engine) | 🔄 Not yet | Planner needs valid step structures; without the engine, step semantics are undefined |
| Pipeline DAG engine (0.5.0) | 📋 Spec only | Generated `pipelines/*.toml` has no execution target |
| LLM provider | ✅ Available | Coding Plan PRO configured for Pi |

## 5. 0.5.1 ADR Assessment

| Dimension | Score | Notes |
|---|---|---|
| **Value** | 8/10 | Eliminates manual Pipeline authoring — a key adoption barrier for non-programmer Factory Directors |
| **Implementation complexity** | 5/10 | ~300 lines Rust (CLI + LLM call + interactive loop + validation); no daemon changes |
| **Risk to MM-CORE** | 0/10 | Planner is a `janus` CLI subcommand, not in the daemon. A Planner crash cannot affect running pipelines. |
| **LLM dependency** | Acceptable | Uses existing Coding Plan provider; no new API keys or services. Fallback: hand-write `pipelines/*.toml` (always works). |
| **Blocked by** | 0.5.0 Pipeline DAG — no execution target without it |

### Verdict

**✅ Include in 0.5.0 scope.** The Planner is high-value (removes the biggest UX barrier for non-programmers), low-risk (CLI-only, not in daemon), and naturally sequenced after 0.5.0. It's the ideal "0.5.0 ship → 0.5.1 polish" feature.
