# ADR-031: Unification of Workflow and Pipeline DSLs

* **Status:** Approved
* **Date:** 2026-08-06
* **Author:** MetaMach Architecture Group
* **Target Version:** 0.5.1 (Deprecation warnings in 0.5.1, default in 0.5.2, hard removal in 0.5.3)
* **Replaces/Amends:** Amends ADR-021 (Pipeline DAG Engine) and ADR-029 (.janus Directory Consolidation)

---

## 1. Context & Problem Statement

在 MetaMach 0.5.0 中，系统强制区分了两个维度的流程抽象：

1. **Workflow (`templates/workflows/*.toml` / `.janus/workflows/*.toml`)**：定义单线顺序（Sequential）的 `WorkflowStep` 列表，映射到 Absurd PG 的 Checkpoint 状态机，负责断点续跑与日志截断。
2. **Pipeline (`templates/pipelines/*.toml` / `.janus/pipelines/*.toml`)**：定义**多节点依赖图（DAG）**，由 `janus::pipeline` 引擎通过 Kahn 拓扑排序算法计算并发层级（Execution Levels），负责跨节点并发调度与多 Agent 异构分配。

这种分层在底层运行时（Engine）具有清晰的物理界限，但在 **开发者体验（DX）与 AI Agent 交互** 侧引发了严重的认知摩擦（Cognitive Friction）：

* **概念重叠与语法仪式感过重（Over-ceremony）**：对于 80% 的日常单线任务（如 `Compile -> Flash -> Test`），用户被强迫同时理解 Workflow 和 Pipeline，甚至需要编写仅包含单个 Workflow 节点的 Pipeline 声明。
* **AI Agent 心理模型失真**：LLM（如 Claude Code、Codex）在生成配置时，经常混淆 `.janus/pipelines/` 和 `.janus/workflows/` 的配置边界，增加上下文纠错成本。
* **文件碎片化**：任务依赖与步骤逻辑散落在不同 TOML 文件中，不利于版本控制与模块复用。

我们需要在**保持底层 Absurd PG Durable Checkpoint 与 Pipeline DAG 并发调度物理能力不变**的前提下，在用户接口与配置（DSL）层彻底合并这两套文件与概念。

---

## 2. Decision

决定在 MetaMach DSL 语法层**彻底废除独立的 Pipeline DSL 文件结构，统一归一化为 Workflow**。

### 核心决议点：

1. **单一概念暴露**：对外（人类开发者、AI Agent、CLI、`.janus/` 目录结构）仅保留 **Workflow** 这一种任务声明规范。所有工作流统一存储于 `.janus/workflows/` 目录下（`templates/workflows/` 作为内建模板）。
2. **渐进式 DSL Schema（Progressive DSL）**：Workflow 声明格式支持两种模式——**单线模式（Linear Mode）** 与 **节点图模式（DAG Mode）**。
3. **精确的分发路径（Shape-Driven Dispatch）**：Linear 模式直接走现有高效路径 `handle_dispatch → spawn_workflow`，**不经过** Kahn 拓扑排序。仅 DAG 模式走 `handle_dispatch_pipeline` 的层级并发调度路径。分发路径由解析后的数据形状决定，非统一转换。
4. **混合节点组合能力（Hybrid Node Composition）**：DAG 模式下的节点既支持引用已有的独立 Workflow 文件（`workflow = "build_test"`），也支持声明内联步骤（inline `steps`）。内联步骤通过进程内临时 Workflow 注册表（In-Process Workflow Register）注入调度器，无需落盘。
5. **明确的持久化界限（Durability Boundary）**：显式延续 ADR-021 的持久化契约——DAG 层级编排属于内存级（Ephemeral Orchestration），每个 DAG 节点（无论是文件引用还是内联步骤）映射为恰好 **一个 Absurd PG 任务（Task）**，该任务内的所有 Step 均保持持久化 Checkpoint。
6. **向后兼容的解析器（Backward-Compatible Deserializer）**：新解析器同时支持旧版 `[workflow]` 带 Header 格式与新版扁平化格式，确保 0.5.0 模板在 0.5.1 中零修改可用。
7. **语义化版本迁移（SemVer Migration）**：采取 0.5.1 (警告) → 0.5.2 (默认) → 0.5.3 (硬性移除) 的渐进迁移策略。

## 3. Detailed Design

### 3.1 统一 Workflow DSL 规范 (`.janus/workflows/*.toml`)

语法设计遵循**渐进式暴露原则（Progressive Disclosure）**。

#### 模式 A：单线模式（Linear Mode — 80% 常用场景）

直接提供顺序 `steps` 数组。该模式由 daemon 识别后**直接走 `handle_dispatch` → `spawn_workflow` 路径**，与 0.5.0 的执行逻辑完全一致，不经过任何 DAG 拓扑排序。

**新格式（0.5.1+）**：

```toml
# .janus/workflows/flash_esp32.toml
[workflow]
name = "flash_esp32"
description = "编译并烧录 ESP32 固件"

[[steps]]
name = "build"
agent = "builder"
command = "cargo build --release --target xtensa-esp32s3-espidf"

[[steps]]
name = "flash"
agent = "builder"
command = "esptool.py --chip esp32s3 write_flash 0x0 target/firmware.bin"

[[steps]]
name = "monitor_test"
agent = "tester"
command = "pytest tests/test_uart.py"
```

> **注意**：保留 `[workflow]` header 格式，与所有 0.5.0 模板完全兼容。安全策略字段（如 `janush_safety`）由 ADR-027（Probe SPI + Policy DSL）单独设计，本 ADR 不引入。

#### 模式 B：DAG 图模式（Advanced DAG Mode — 20% 复杂场景）

当需要多 Agent 协作、跨模型对齐或并行执行时，改用 `nodes` 数组，并通过 `needs` 声明依赖关系。该模式由 daemon 识别后走 `handle_dispatch_pipeline` 路径。

节点支持两种互斥的步骤来源：
- **`workflow = "<name>"`**：引用已有的独立 Workflow 文件（现有 0.5.0 行为，完全保留）。
- **`steps = [...]`**：内联定义步骤列表。daemon 将其注册为进程内临时 Workflow 对象，注入调度器。

```toml
# .janus/workflows/adversarial_audit.toml
[workflow]
name = "adversarial_audit"
description = "多异构 Agent 对抗审查与自动构建"

# 节点 1：Kimi 模型代码审查（内联 Step）
[[nodes]]
id = "audit_kimi"
steps = [
  { name = "run_review", agent = "auditor_kimi", command = "janus-review --model kimi-k3 --target src/" }
]

# 节点 2：MiniMax 模型并行审查（无 needs，与 audit_kimi 并行；内联 Step）
[[nodes]]
id = "audit_minimax"
steps = [
  { name = "run_review", agent = "auditor_minimax", command = "janus-review --model minimax-code --target src/" }
]

# 节点 3：依赖节点 1 和 2，通过 workflow 字段复用独立的 flash_esp32 Workflow
[[nodes]]
id = "build_and_flash"
needs = ["audit_kimi", "audit_minimax"]
workflow = "flash_esp32"

# 节点 4：后续测试节点，使用内联 Step
[[nodes]]
id = "post_verify"
needs = ["build_and_flash"]
steps = [
  { name = "system_check", agent = "tester", command = "janus-health-check" }
]
```

> **节点模式互斥规则**：在 DAG 节点的定义中，`workflow` 属性与 `steps` 属性互斥。若同时指定，解析器抛出错误。

### 3.2 向后兼容的双格式解析器（Backward-Compatible Deserializer）

现有 0.5.0 Workflow 模板全部使用 `[workflow]` header 格式（如 `templates/workflows/wf_architect_design.toml`），现有 Pipeline 模板全部使用 `[pipeline]` header 格式（如 `templates/pipelines/spec2software.toml`）。解析器必须同时支持三种格式。

#### 解析策略

在 `recipe.rs` 中引入统一解析入口 `load_unified_workflow()`，使用尝试性解析（try-parse）策略：

```rust
/// 统一 Workflow 解析结果
pub enum UnifiedWorkflow {
    /// 单线模式：直接走 handle_dispatch → spawn_workflow
    Linear(Workflow),
    /// DAG 模式：走 handle_dispatch_pipeline 层级调度
    Dag {
        config: PipelineConfig,
        /// 节点内联步骤注册表：node_id → 临时 Workflow 对象
        inline_register: HashMap<String, Workflow>,
    },
}

/// 统一加载入口，兼容所有格式
pub fn load_unified_workflow(name: &str, repo_root: &Path) -> Result<UnifiedWorkflow> {
    let path = resolve_workflow_path(name, repo_root)?;
    let text = std::fs::read_to_string(&path)?;

    // 1. 尝试解析为 DAG 格式（包含 [workflow] + [[nodes]]）
    if let Ok(dag) = toml::from_str::<DagWorkflowFile>(&text) {
        if !dag.nodes.is_empty() {
            return parse_dag_workflow(dag, repo_root);
        }
    }

    // 2. 尝试解析为旧版 Pipeline 格式（[pipeline] + [[nodes]]）
    if let Ok(pipeline) = toml::from_str::<LegacyPipelineFile>(&text) {
        if !pipeline.nodes.is_empty() {
            warn!("Pipeline format is deprecated; migrate to unified Workflow DAG mode");
            return convert_legacy_pipeline(pipeline);
        }
    }

    // 3. 默认：解析为标准 Workflow（[workflow] + [[steps]]）
    let wf: Workflow = toml::from_str(&text)?;
    Ok(UnifiedWorkflow::Linear(wf))
}

/// 旧版 [pipeline] 格式桥接：所有节点均为文件引用（无内联步骤）
fn convert_legacy_pipeline(legacy: LegacyPipelineFile) -> Result<UnifiedWorkflow> {
    let config = PipelineConfig {
        pipeline: legacy.pipeline,
        nodes: legacy.nodes,           // PipelineNode { id, workflow, needs } 原样透传
    };
    config.validate()?;
    Ok(UnifiedWorkflow::Dag {
        config,
        inline_register: HashMap::new(), // 旧版无内联步骤
    })
}
```

这保证了：
- **所有 11 份 `templates/workflows/*.toml`**：解析为 `UnifiedWorkflow::Linear(Workflow)`，原样走 `handle_dispatch`。
- **所有 3 份 `templates/pipelines/*.toml`**：在 0.5.1 中发出 Deprecation Warning 后桥接为 `UnifiedWorkflow::Dag`（所有节点均为文件引用，`inline_register` 为空）。
- **新的统一 DAG 格式**：直接解析为 `UnifiedWorkflow::Dag`。

#### 中间解析结构

```rust
/// DAG 模式 Workflow 文件格式（新格式）
#[derive(Deserialize)]
struct DagWorkflowFile {
    workflow: WorkflowSection,        // 复用现有 [workflow] header
    #[serde(default)]
    nodes: Vec<DagNodeDef>,
}

/// DAG 节点定义
#[derive(Deserialize)]
struct DagNodeDef {
    id: String,
    #[serde(default)]
    needs: Vec<String>,
    /// 引用外部 Workflow 文件（与 steps 互斥）
    workflow: Option<String>,
    /// 内联定义的 Step 列表（与 workflow 互斥）
    steps: Option<Vec<WorkflowStep>>,
}

/// 旧版 Pipeline 文件格式（兼容层）
#[derive(Deserialize)]
struct LegacyPipelineFile {
    pipeline: PipelineMeta,           // [pipeline] header
    nodes: Vec<PipelineNode>,         // [[nodes]] with { id, workflow, needs }
}
```

> **关键设计约束**：不引入任何新的公开类型到 `recipe.rs` 的导出面。`UnifiedWorkflow::Linear` 返回的就是现有 `Workflow` 类型，直接兼容 `ValidatedRecipe`、`spawn_workflow`、`run_workflow` 的全部调用签名。中间解析结构（`DagWorkflowFile`、`DagNodeDef`）均为 `recipe.rs` 模块内部私有类型。

### 3.3 内联步骤的进程内 Workflow 注册表（In-Process Register）

DAG 模式中带有 `steps = [...]` 的节点需要一条不依赖文件系统的分发路径。

#### 物理路径问题

当前 `handle_dispatch_pipeline` 对每个 DAG 节点调用：
```rust
handle_dispatch(db, repo_root, &blueprint, Some(&node.workflow), params)
```
该函数内部调用 `load_workflow(node.workflow, repo_root)` 在磁盘搜索 `.toml` 文件。内联步骤没有对应的磁盘文件，因此需要一条旁路。

#### 解决方案：临时 Workflow 注册表

在 `UnifiedWorkflow::Dag` 变体中随 `PipelineConfig` 一同返回 `inline_register: HashMap<String, Workflow>`。每个内联节点在解析阶段被合成为一个标准 `Workflow` 对象，键名为 `__inline_{node_id}`：

```rust
fn parse_dag_workflow(dag: DagWorkflowFile, repo_root: &Path) -> Result<UnifiedWorkflow> {
    let mut pipeline_nodes = Vec::new();
    let mut inline_register: HashMap<String, Workflow> = HashMap::new();

    for node in dag.nodes {
        match (node.workflow, node.steps) {
            (Some(wf_name), None) => {
                // 文件引用节点：保留现有行为
                pipeline_nodes.push(PipelineNode {
                    id: node.id,
                    workflow: wf_name,
                    needs: node.needs,
                });
            }
            (None, Some(steps)) => {
                // 内联步骤节点：合成临时 Workflow 并注册
                let synthetic_name = format!("__inline_{}", node.id);
                let synthetic_workflow = Workflow {
                    workflow: WorkflowSection {
                        name: synthetic_name.clone(),
                        description: Some(format!("Inline steps for DAG node '{}'", node.id)),
                    },
                    steps,
                };
                // 复用与 load_workflow 相同的校验逻辑（非空步骤、name/agent 必填等）
                validate_workflow(&synthetic_workflow)?;
                inline_register.insert(synthetic_name.clone(), synthetic_workflow);
                pipeline_nodes.push(PipelineNode {
                    id: node.id,
                    workflow: synthetic_name,
                    needs: node.needs,
                });
            }
            (Some(_), Some(_)) => bail!("Node '{}': cannot specify both 'workflow' and 'steps'", node.id),
            (None, None) => bail!("Node '{}': must specify either 'workflow' or 'steps'", node.id),
        }
    }

    let config = PipelineConfig {
        pipeline: PipelineMeta {
            name: dag.workflow.name,
            description: dag.workflow.description,
        },
        nodes: pipeline_nodes,
    };
    config.validate()?; // Kahn 算法环路与依赖校验

    Ok(UnifiedWorkflow::Dag { config, inline_register })
}
```

#### Daemon 分发改造

`handle_dispatch_pipeline` 在逐层分发节点时，优先查询注册表：

```rust
async fn handle_dispatch_pipeline(
    db: &AbsurdDb,
    repo_root: &Path,
    blueprint: &str,
    config: &PipelineConfig,
    inline_register: &HashMap<String, Workflow>,
) -> Result<Response> {
    let plan = config.plan()?;
    for level in &plan.levels {
        let mut handles = Vec::new();
        for node in level {
            let workflow = if let Some(wf) = inline_register.get(&node.workflow) {
                // 内联节点：直接使用注册表中的 Workflow 对象
                wf.clone()
            } else {
                // 文件引用节点：从磁盘加载（现有路径）
                load_workflow(&node.workflow, repo_root)?
            };
            // 后续流程与现有 handle_dispatch 完全一致：
            //   validate → spawn_workflow → tokio::spawn(run_workflow)
            handles.push(dispatch_node(db, blueprint, workflow, repo_root));
        }
        futures::future::join_all(handles).await;
    }
    Ok(Response::Ok)
}
```

> **PG 任务映射规则**：每个 DAG 节点（无论文件引用还是内联步骤）恰好产生 **一个 Absurd PG 任务（Task）**。该任务的 `steps` 字段包含该节点的全部 `WorkflowStep` 列表。节点内的每个 Step 在执行期间生成 `metamach_step_meta` 行，享受完整的 Checkpoint 与断点续跑保护。这与 0.5.0 中 `handle_dispatch_pipeline` 为每个节点产生一个独立 Workflow Task 的行为完全一致。

### 3.4 Shape-Driven Dispatch：Daemon 主分发逻辑

在 `janus_daemon.rs` 的 `handle_request()` 中，按照解析后的数据形状分发：

```rust
Request::Dispatch { blueprint, workflow, pipeline } => {
    let name = workflow
        .or(pipeline.map(|p| { warn!("--pipeline is deprecated; use --workflow"); p }))
        .unwrap_or_else(|| recipe.blueprint.default_workflow.clone());

    match load_unified_workflow(&name, repo_root)? {
        UnifiedWorkflow::Linear(wf) => {
            // 80% 路径：直接走现有高效路径，跳过 Kahn 排序
            // 传入预加载的 Workflow 对象，不再从磁盘二次加载
            dispatch_workflow(db, repo_root, &blueprint, &wf).await
        }
        UnifiedWorkflow::Dag { config, inline_register } => {
            // 20% 路径：Kahn 拓扑排序 + 层级并发调度
            handle_dispatch_pipeline(db, repo_root, &blueprint, &config, &inline_register).await
        }
    }
}
```

**实现说明**：现有 `handle_dispatch` 函数签名为 `handle_dispatch(db, repo_root, blueprint, workflow: Option<&str>)`，内部调用 `load_workflow(name)` 从磁盘加载。Linear 分支已持有预加载的 `Workflow` 对象，因此需要提取一个 `dispatch_workflow(db, repo_root, blueprint, wf: &Workflow)` 辅助函数，接受预加载的 `Workflow` 直接进入 `validate → spawn_workflow → run_workflow` 路径。`handle_dispatch` 重构为：先调用 `load_workflow` 获取 `Workflow`，再委托 `dispatch_workflow`。DAG 路径中 `handle_dispatch_pipeline` 的节点分发同样调用 `dispatch_workflow`（文件引用节点先 `load_workflow`，内联节点查 `inline_register`）。

**这确保了 Linear 模式不经过任何 DAG 转换或 Kahn 排序**——直接走现有 `handle_dispatch` 路径，与 0.5.0 行为完全一致。

### 3.5 UDS 协议与 CLI 命令适配

#### 1. UDS 协议 (`protocol.rs`)

现有 `Request::Dispatch` 变体保持不变。`pipeline` 字段标记为 Deprecated：

```rust
pub enum Request {
    Dispatch {
        blueprint: String,
        workflow: Option<String>,
        /// [Deprecated in 0.5.1] 映射至 workflow 参数处理
        #[serde(skip_serializing_if = "Option::is_none")]
        pipeline: Option<String>,
    },
    // ... 其他变体保持不变
}
```

#### 2. CLI 命令收敛 (`bin/janus.rs`)

| 原 CLI 指令 (v0.5.0) | 新 CLI 指令 (v0.5.1+) | 说明 |
| --- | --- | --- |
| `janus dispatch --workflow <wf>` | **`janus start <wf>`** / **`janus start --workflow <wf>`** | 统一派发入口（daemon 按数据形状自动选择 Linear / DAG） |
| `janus dispatch --pipeline <pl>` | **`janus start <wf>`** | `--pipeline` 变为废弃别名，重定向至 `--workflow` 路径 |
| `janus pipeline validate <pl>` | **`janus start --dry-run <wf>`** | 对 DAG 拓扑结构进行预览与静态校验 |
| *(无)* | **`janus start --inline "cmd"`** | 快捷模式（见下） |
| `janus pipeline plan` / `janus plan` | **`janus pipeline plan`** / **`janus plan`** | 保留为 LLM 辅助流水线生成器 (ADR-023)，不受影响 |

#### 3. `--inline` 快捷指令规范

`janus start --inline "cargo test"` 的底层语义：
1. 在进程内构造一个临时 `Workflow` 对象：`name = "inline_<short_uuid>"`, `steps = [{ name: "run", agent: "builder", command: "cargo test" }]`。
2. 继承当前项目的默认 Blueprint (`.janus/blueprint.toml`)。
3. 走 `UnifiedWorkflow::Linear` 路径，在 Absurd PG 中创建持久化 Task，挂载 tmux 会话，享受 Tool Guard 与 Checkpoint 保护。
4. 进程退出后临时 Workflow 对象不留存。PG 中的 Task 记录与 `metamach_step_meta` 行按正常生命周期保留。

### 3.6 类型命名与调用面影响

本 ADR 不引入任何与现有 `recipe.rs` 导出类型冲突的公开类型名。

| 现有类型 (0.5.0) | 本 ADR 影响 | 说明 |
| --- | --- | --- |
| `Workflow` | **保留不变** | `UnifiedWorkflow::Linear` 返回的就是这个类型 |
| `WorkflowSection` | **保留不变** | `[workflow]` header 解析 |
| `WorkflowStep` | **保留不变** | DAG 内联节点复用同一类型，无字段变更 |
| `ValidatedRecipe` | **保留不变** | `validate()` 签名不变，仍接收 `Workflow` |
| `PipelineConfig` | **保留不变** | DAG 路径复用现有 pipeline 引擎 |
| `PipelineNode` | **保留不变** | `{ id, workflow, needs }` 结构不变 |
| *(新增)* `UnifiedWorkflow` | 新增枚举 | `recipe.rs` 公开导出，仅在 daemon 分发层使用 |
| *(新增)* `DagWorkflowFile` | 新增 `pub(crate)` | 模块内部解析中间类型 |
| *(新增)* `DagNodeDef` | 新增 `pub(crate)` | 模块内部解析中间类型 |
| *(新增)* `LegacyPipelineFile` | 新增 `pub(crate)` | 旧版兼容解析类型 |

受影响的调用面：
- `janus_daemon.rs:handle_request()` — 增加 `load_unified_workflow` 分支。
- `janus_daemon.rs:handle_dispatch_pipeline()` — 增加 `inline_register` 参数。
- `janus.rs:dispatch()` — `--pipeline` 参数标记废弃。
- 其余所有调用签名（`spawn_workflow`、`run_workflow`、`validate`、`ValidatedRecipe`）**完全不变**。

## 4. Migration & Backward Compatibility Strategy

三阶段渐进式迁移计划：

```text
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │  Phase 1 (v0.5.1): 双轨兼容与弃用警告 (Dual-Track Support & Warnings)       │
```

## 5. Consequences

### Positive (收益)

* **认知负荷大幅降低**：开发者与 AI Agent 只需掌握 Workflow 一个概念，从单线步骤到多节点 DAG 均在同一文件格式中渐进式展开。
* **零回归风险**：Linear 模式走与 0.5.0 完全相同的 `handle_dispatch` → `spawn_workflow` 路径，不经过 DAG 引擎。
* **完整的模块化复用**：DAG 节点既可引用已有 Workflow 文件（`workflow = "build_test"`），也可内联定义步骤——满足构图灵活性与组件复用的双重需求。
* **零模板破坏**：向后兼容解析器确保所有 14 份 0.5.0 模板无修改可用。

### Negative / Risks (风险与代价)

* **解析器复杂度提升**：`load_unified_workflow` 需要尝试性解析（try-parse）三种格式，并维护 `inline_register` 语义。
* **进程内注册表生命周期**：`inline_register` 的 `Workflow` 对象仅存在于当前 dispatch 调用栈中。若 daemon 在 DAG 层级间崩溃重启，冷启动恢复路径需要重新解析原始 TOML 文件以重建注册表（这与现有 `handle_dispatch_pipeline` 的非持久化特性一致——ADR-021 已接受此限制）。
* **文档校准**：需更新 `docs/` 下 `ARCH.md`、`Feature-Spec.md` 以及 `templates/` 下的 14 份模板文件。
